# 四项目 task-list 归纳标准

本文基于四组样本整理：

- PDF Markdown Skill：`docs/discussion/1-skills-pdf-markdown/task-list(pdf-markdown).md`
- PRD Workflow：`docs/discussion/2-prd-workflow/task-list(prd-workflow).md`
- Translation Workflow：`docs/discussion/3-translation-workflow/task-list(translation).md`
- Patent Workflow：`docs/discussion/4-patent-workflow/task-list(patent).md`

## 共同点

1. `task-list.md` 是项目级任务台账，不是随手日志。
2. 文件头承担轻量 schema 职责：说明记录范围、动作枚举、同义归并规则。
3. 动作字段统一收敛为 8 个值：`修复`、`开发`、`优化`、`调整`、`规划`、`检查`、`文档`、`运维`。
4. 主体结构是 `## 二级分类 + Markdown 表格`。
5. 基础字段都是 `ID / 动作 / 描述 / 发现时间 / 完成时间 / 状态 / 备注`。
6. Bug 类通常使用 `问题描述`，非 Bug 类通常使用 `事项`。
7. 时间字段统一拆成 `发现时间` 和 `完成时间`，格式为 `YYYY-MM-DD HH:MM`，使用机器本地时区的 24 小时制时间。
8. `备注` 是信息密度最高的字段，承载根因、实现摘要、影响文件、测试结果、审查来源和后续说明。
9. ID 采用 `PREFIX-三位编号`，要求递增、不复用（含已归档到 `*archive*.md` 的编号）、避免重复。

## 差异点

| 维度 | 差异 | 推荐处理 |
| --- | --- | --- |
| 分类命名 | `功能开发` vs `开发事项`，`文档维护` vs `文档事项` | 默认用 `功能开发` / `文档维护`；如已有项目用另一套命名，保留原习惯 |
| 分类集合 | 有的项目包含 `规划事项`、`优化事项`、`调研事项`、`配置运维` | 默认只启用常用 7 类；额外分类按需添加 |
| 开发字段 | 专利项目使用 `优先级`、`预计时间` 两个扩展列 | 仅在项目需要排期或 WBS 管理时启用 |
| 状态模型 | 有的只有终态，有的包含 `待修复`、`待开发` | 默认支持活跃状态，但不要强迫旧完成台账改造 |
| 统计摘要 | 专利项目有摘要，其他项目没有 | 作为可选扩展，不设为默认必需 |
| 历史质量 | PRD/专利样本存在重复 ID、重复章节、空表头、未转义竖线 | CLI 和人工检查都应覆盖这些风险 |

## 推荐统一模型

### 默认分区

| 分区 | 前缀 | 主要用途 |
| --- | --- | --- |
| 代码 Bug | `BUG` | 缺陷、回归、安全风险、错误行为 |
| 调整事项 | `ADJ` | 需求口径、项目定位、配置/规范调整 |
| 检查事项 | `CHK` | 审计、复核、验证、代码审查、评估 |
| 测试数据 | `TST` | 测试样本、夹具数据、测试输出、验证数据集 |
| 文档维护 | `DOC` | 文档新增、修订、归档、结构说明 |
| 功能开发 | `DEV` | 新功能、模块建设、工程能力 |
| 配置运维 | `OPS` | 环境、部署、依赖、Git、配置维护 |

### 可选分区

| 分区 | 前缀 | 启用条件 |
| --- | --- | --- |
| 规划事项 | `PLN` | 项目有路线图、阶段计划、WBS、方案沉淀 |
| 优化事项 | `OPT` | 优化/重构事项很多，不适合混在开发或 Bug 中 |
| 调研事项 | `RES` | 项目经常记录外部资料、竞品、开源项目或专利调研 |
| 统计摘要 | 无 | 项目需要显式追踪完成率或待处理数量 |

## 字段定义

### 通用 7 列

| 字段 | 定义 | 规则 |
| --- | --- | --- |
| `ID` | 任务唯一编号 | `<前缀>-<三位数字>`，如 `BUG-001` |
| `动作` | 事项性质 | 只能使用 8 个动作枚举 |
| `问题描述 / 事项` | 一句话描述 | Bug 用 `问题描述`，其他默认用 `事项` |
| `发现时间` | 事项被发现、提出或登记的时间 | 格式为 `YYYY-MM-DD HH:MM`，24 小时制，默认使用机器本地时区 |
| `完成时间` | 事项完成、修复或关闭的时间 | 格式为 `YYYY-MM-DD HH:MM`；未完成事项填 `-` |
| `状态` | 当前状态 | Bug 完成态用 `已修复`，非 Bug 完成态用 `已完成` |
| `备注` | 细节说明 | 写清根因、改动、文件、测试、来源 |

### 开发 9 列扩展

```markdown
| ID | 动作 | 事项 | 优先级 | 预计时间 | 发现时间 | 完成时间 | 状态 | 备注 |
```

适用于 WBS、专利工作流、长期工程计划等需要排期的项目。

## 状态建议

| 状态 | 适用场景 |
| --- | --- |
| `待修复` | Bug 已记录但尚未修复 |
| `已修复` | Bug 已修复并验证 |
| `待办` | 通用未完成（文档/运维/检查/调整/优化/规划等非 Bug 待办的首选） |
| `待开发` | 功能开发类尚未开始（也可用 `待办`） |
| `进行中` | 已开始但未完成 |
| `已完成` | 非 Bug 任务完成 |
| `已解决` | 排查类事项已定位并闭环；新条目优先用 `已完成`，仅在明确描述故障排查闭环时使用 |
| `已关闭` | 作废、不处理、被其他条目替代 |

如果项目只想维护“完成台账”，可以只使用 `已修复` 和 `已完成`。`已解决`、`已修复`、`已完成`、`已关闭` 都按完成态统计。未完成态：`待修复`/`待办`/`待开发`/`进行中`。`check` 对非标准状态（如「待处理」）会附带建议映射（如 → `待办` / `待开发`）。

## 条目互引

备注/描述中可用 wiki 风格互引：`[[BUG-001]]`、`[[DOC-036]]`。`check` 会检测悬空引用（指向不存在的 ID）。归档后主表不再含该 ID，引用它的条目会被标悬空——归档前宜先清理或改写互引。

## 记录方案

新增记录时按以下顺序处理：

1. 判断事项类型，选择分区。
2. 将动作归并到 8 个标准枚举之一。
3. 搜索当前前缀最大 ID，分配下一个三位编号。
4. 写一句可追踪的描述。
5. 填写发现时间，格式为 `YYYY-MM-DD HH:MM`，使用机器本地时区。
6. 填写完成时间；已完成事项使用 `YYYY-MM-DD HH:MM`，未完成事项用 `-`。
7. 填写真实状态。
8. 在 `备注` 写关键证据：文件、命令、测试、审查来源和后续风险；交叉引用用 `[[ID]]`。
9. 如有统计摘要，同步更新摘要。

## 已有列表标准化

`standardize` 用于已经运行一段时间的 `task-list.md`。它不是简单套模板，而是先诊断，再决定是否修复。

以下命令在 Windows 上把 `python3` 替换为 `python`。

默认只生成报告，不修改文件：

```bash
python3 skills/task-list-initialization/scripts/task_list_cli.py standardize --file task-list.md --report docs/task-list-standardize-report.md
```

报告应覆盖：

| 维度 | 检查内容 |
| --- | --- |
| 结构合规 | 非法 ID 格式（如 `bug-001`）、重复 ID、重复章节、坏表格行、动作/状态枚举、表头是否符合当前 7 列时间模型；**预览安全**：表内空行（围栏代码除外）、单元格裸 HTML、未按 CommonMark 闭合的反引号 span |
| 日期 schema 变体 | 文件用双日期（`发现时间/完成时间`）还是合法的单日期（`完成日期`，6 列）；按文件实际 schema 校验，单日期好文件应通过而非全量报表头不一致 |
| 记录完整性 | 备注是否有证据、完成记录是否有完成时间、未完成记录是否误填完成时间 |
| 分类清晰度 | ID 前缀与所在章节是否一致，调研/优化/文档/运维事项是否混放 |
| Profile 建议 | 是否继续使用 `minimal`，或升级为 `planning`、`extended`、`development` |
| 可自动修复 | 缺失空分区、表内空行、旧单日期 schema 迁移等低风险事项 |
| 维护规则状态 | 是否已安装「会话结束任务同步」规则（CLAUDE.md/AGENTS.md，双写告警）、可选 Stop hook、**按工具**声明 vs 实际（Claude hook 不能顶替 Codex 声明）、hook 是否使用 `${CLAUDE_PROJECT_DIR}`、`.gitignore` 是否忽略整个 `.claude/`；缺失时由 agent 询问用户后优先用 `install-maintenance` 安装 |
| 需人工确认 | 重命名章节、移动记录、重写重复 ID、拆分语义混杂事项 |

修复必须显式开启：

| 参数 | 行为 |
| --- | --- |
| `--apply-safe-fixes` | 执行低风险修复，例如补齐缺失空分区、删除表内空行（**不改围栏代码**）、转义单元格内未转义的 `|` |
| `--migrate-schema` | 将可无损迁移的旧单日期列升级为双日期：`发现日期`→仅发现时间、`完成日期`→仅完成时间（保持日精度、禁止跨语义复制）；`开始日期`/`规划日期` 拒绝并说明无法映射 |
| `--fix-only` | 输出修饰：仅打印修复摘要、不展开完整诊断报告；本身不触发修复，需配合 `--apply-safe-fixes` 或 `--migrate-schema` |

`--migrate-schema` 只迁移表头能对齐的行。若某数据行列数与表头不符（几乎总是单元格里未转义的 `|` 把一个单元格劈成两半），它无法安全重排这些格子，会**保留原行并告警**（在 `--fix-only` 摘要和 `--format json` 的 `migrate_warnings` 字段中按 ID + 行号 + 列数列出），而不是静默漏报。遇到这类告警应先手工转义 `|` 或修正列数，再重跑迁移。

标准化时应保留历史事实。不要为了贴合模板自动改写事项含义、移动记录、合并重复 ID 或重算摘要，除非用户明确批准。发现「开源项目调研」时建议改名为「调研事项」并**整段移到「优化事项」之后**；已知章节顺序偏离模板时给出质量提示，但不自动搬迁。

## 样式约定

- 使用 Markdown 表格，不使用 bullet list 代替正式记录。
- 每个分区只保留一张表。
- 表头后必须有分隔行。
- **同一张表的 `|` 数据行之间禁止空行**（空行只允许出现在表与下一 `##` 之间）。CommonMark/GFM 里空行结束表格，后续 `| ... |` 不再属于同一张表。`check` 按原始行扫描并判失败，但**跳过围栏代码块**；`standardize --apply-safe-fixes` 会删除「数据行 ↔ 数据行」之间的空行，**不得改写围栏内的示例表格**。
- 表格单元格里的 `|` 必须写成 `\|`。
- **单元格禁止裸 HTML 标签**（会改变文档流的标签：`<title>`、`<details>`、`<script>`、`<style>`、`<textarea>`、`<svg>`、`<html>`、`<head>`、`<body>`、`<table>`、`<iframe>`、`<xmp>`、`<noembed>`、`<noframes>`、`<plaintext>`）。必须写成 `` `<title>` `` 或 HTML 实体。不要把所有 `<` 都当标签：`<id>`、`a < b` 可以保留。
- **每一行反引号必须按 CommonMark 配对**：长度为 n 的 opener 匹配下一处恰好 n 个未转义反引号的 closer；双反引号 span 内可以包含单反引号。仅统计字符个数的奇偶不够——两个反引号但没有闭合 delimiter 仍应失败。反斜杠转义的反引号视为字面量。
- Agent 若手改 md（不走 CLI），改完必须再跑 `check`。`check` 通过不应再等于「预览一定正常」——它必须能抓到表内空行、裸 HTML 和未闭合的反引号 span。
- 路径、命令、代码标识用反引号。
- 备注可以长，但应优先写结构化事实，不写空泛总结。

## 语言版本（中文 / English）

task-list 支持两种语言：**中文（简体，`zh`，默认）** 与 **英文（`en`）**。英文版是中文版的忠实翻译：分区集合、ID 前缀（`BUG-`/`ADJ-`/…）、7 列结构完全一致，仅标签不同。`init --lang zh|en` 选择新建语言；`add`/`check`/`summary`/`standardize` 自动按文件结构检测语言，无需传 `--lang`。The task-list supports two languages: Chinese (Simplified, `zh`, default) and English (`en`). The English version is a faithful translation: same section set, same ID prefixes, same 7-column model; only labels differ. `init --lang` picks the language for new files; the other subcommands auto-detect it.

| 中文 | English |
| --- | --- |
| 代码 Bug / 调整事项 / 检查事项 / 测试数据 / 文档维护 / 功能开发 / 配置运维 | Bugs / Adjustments / Reviews / Test Data / Docs / Features / Ops |
| 规划事项 / 优化事项 / 调研事项 / 统计摘要 | Plans / Optimizations / Research / Summary |
| 动作 / 事项 / 问题描述 / 发现时间 / 完成时间 / 状态 / 备注 | Action / Item / Description / Found / Done / Status / Notes |
| 修复·开发·优化·调整·规划·检查·文档·运维 | Fix·Develop·Optimize·Adjust·Plan·Review·Doc·Ops |
| 待修复·已修复·待办·待开发·进行中·已完成·已解决·已关闭 | Pending Fix·Fixed·Todo·Pending Dev·In Progress·Done·Resolved·Closed |

Bug 分区中文用 `问题描述`、英文用 `Description`；其余分区中文用 `事项`、英文用 `Item`。The Bug section uses `问题描述`/`Description`; other sections use `事项`/`Item`. 终态（已完成态）：`已修复`/`已完成`/`已解决`/`已关闭` ↔ `Fixed`/`Done`/`Resolved`/`Closed`.

## 日期 schema 变体（双日期 / 单日期）

规范模型是**双日期**：`发现时间` + `完成时间`（含 `HH:MM`），7 列。但有的项目合理地保留旧**单日期** schema：单列 `完成日期` / `发现日期`（及历史 `开始日期` / `规划日期`；仅日期，6 列；或 8 列开发扩展），不迁移到双日期。

区分两层能力：

- **兼容校验（能读能追加）**：`check` / `add` 接受上述全部单日期标签；`发现日期` 语义下未完成记录也可写入日期。
- **可无损迁移（能改写 schema）**：仅 `发现日期`→发现时间（完成时间=`-`）、`完成日期`→完成时间（发现时间=`-`）；保持日精度、不补造 `00:00`、不跨语义复制。`开始日期` / `规划日期` 只报告、不写入。

CLI 不强行套双日期：

- `check` / `standardize` 自动检测文件用哪种 schema（任一分区表头同时含 `发现时间`+`完成时间` → 双；否则含任一单日期别名 → 单；都没有则默认双），并按文件实际 schema 校验。单日期的好文件应通过 check，而非每个分区都报「表头与标准不一致」。
- 可用 `--schema auto|dual|single` 覆盖（默认 `auto`）。
- 报告中若检测到单日期，会提示可用 `--migrate-schema` 升级为双日期（需批准，不自动迁移）。
- `add` 同样按目标分区表头识别 schema，并输出对应列数的行（单日期 6 列 / 双日期 7 列 / 开发 8–9 列）；`完成日期` 语义下未完成填 `-`，`发现日期` 语义下未完成仍写入发现日。

## 常见问题和处理

| 问题 | 处理 |
| --- | --- |
| 重复 ID | 不继续复用；如需清理，新增 `ADJ-` 记录说明改号映射 |
| 重复章节 | 合并到同名第一节，并保留条目原始顺序或按 ID 排序 |
| 空表头 | 删除多余表头，只保留一个有效表 |
| ID 前缀与章节不一致 | 新增记录必须一致；历史数据是否移动需用户确认 |
| 非法 ID 格式 | `check` 检出形如 `bug-001`/`BUG-12` 的非法 ID（首列「像 ID 但不符合 `大写前缀-三位数字`」）并报错，不再静默跳过；修正为 `BUG-001` 格式 |
| add 遇非标准表头 | `add` 对表头不符合任一标准 schema 的分区（如列顺序错位的 `ID / 状态 / 动作 / …`）拒绝写入，避免按列数猜测把数据填进错误列；请**手工修正列顺序**后再 `add`。`--migrate-schema` 仅升级受支持的 6/8 列单日期旧 schema，不会重排错位的双日期表头 |
| 状态枚举混乱 | 先定义状态集合，再批量规范 |
| 备注破坏表格 | 转义 `|`；单元格禁止裸 `<title>`/`<details>`/`<iframe>` 等流式 HTML（写成 `` `<title>` ``）；反引号按 CommonMark 成对闭合；`standardize --apply-safe-fixes` 可删除表内空行（围栏代码除外），并可合并转义备注/描述中未转义的 `|`（在状态与时间列仍可对齐时）。`check` 对表内空行、裸 HTML、未闭合反引号 span 判失败 |
| 主表过长 | `archive --older-than-days N` 将已完成且超过 N 天的记录移到 `task-list-archive-YYYYMM.md`；主表只留活跃与近期条目。`add` 分配下一 ID 时会扫描同目录 `*archive*.md`，避免复用已归档编号 |
| 悬空互引 | `check` 检测 `[[ID]]` 指向不存在的 ID；归档或删改后需同步清理引用 |
